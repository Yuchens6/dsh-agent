# 高并发支持：第十二阶段

本阶段交付可配置并发、背压与基准工具，不承诺单节点达到 10,000 QPS（每秒请求数），也不代表 10,000 个模型对话可以同时执行。它们是不同的容量目标。

## 服务边界与已实现能力

| 服务 | 本阶段职责 | 不承担的职责 |
| --- | --- | --- |
| API（前端聚合服务） | 单副本在途请求上限；认证与正文解析前拒绝过载；断开释放；超时保护；传递重试等待秒数 | 不持久化排队，不计费；不是跨副本全局请求限流 |
| Chat（会话服务） | 数据库统一执行用户新消息频率与未投递积压限制；同事务保存消息、运行请求及审计；可并行发布不同会话 | 不访问运行数据库；未投递积压不等于整个系统待执行任务数 |
| Run Control（运行控制服务） | 全局、公司、用户调度槽位；等待老化优先；有界并行回写结果及支撑票据；独立超时清理 | 不计算模型费用，不绕过配额服务；暂未分片消息消费 |
| Runtime DSH（DSH 执行服务） | 每副本多个受控执行槽，每槽一次领取一个任务，无额外预取；停机取消并等待所有槽清理 | 不允许用户任意代码，不自动重跑失败模型 |
| Quota（配额与积分服务） | 继续作为并发、日预算与积分预留的最终裁决者，维持计量及幂等账本 | 本阶段不改变收费语义，不增加共享账户自动透支 |

保持独立服务和纯协议包。后台循环、数据库容量保护由所属服务自行持有，没有跨服务导入业务代码或查询其他数据库模式。

## 1. 请求接收与拒绝

API 每副本默认最多 128 个在途业务请求，不建立应用层等待队列。超过上限返回 HTTP 503（服务暂不可用）及 `Retry-After: 1`（建议一秒后重试）。内部健康探针不占用业务槽位。连接无活动超时 15 秒，接收请求超时 30 秒；这些限制不能替代网关的连接、请求体和恶意请求防护。

单副本门禁不等于全局用户限流。所有业务路径的身份校验、跨用户隔离仍保持；这里只削减下游过载。多个 API 副本的总接收上限约为副本数乘单副本上限，必须随下游和数据库容量一起规划。

Chat 根据认证主体的 `tenantId`（公司标识）和 `uid`（用户标识）执行跨副本的新消息限制：

- 默认每用户 60 秒窗口内最多 120 条新消息。窗口从该用户首条计数消息开始，以数据库时间为准；窗口边界可能产生两倍短时突发，不是平滑速率保证。
- 默认每用户最多 1000 条、每会话最多 100 条尚未投递到 NATS（消息系统）的运行请求。
- 同一用户跨会话、跨 Chat 副本共用计数行；不同公司同名用户分开计算。
- 先检查身份、既有幂等记录和归档状态，再检查新消息额度。确认丢失后的成功请求重放不重复消耗频率，不因积压满而无法取回旧确认。
- 新消息、限流计数、事务发件箱及审计一起提交；拒绝或数据库失败全部回滚。返回 429（请求过多）时提供建议等待时间。

频率限制只覆盖新用户消息，不是所有读取、会话创建或文件操作的全局限流。积压限制只覆盖 Chat 本地尚未投递的运行请求：消息代理成功接收后，额度即可释放，**不会限制已经进入运行控制数据库的等待队列**。不能以此宣称全链路积压已严格有界。

客户端必须保持原 `Idempotency-Key`（幂等键）和请求正文，等待重试时间并加入随机抖动；不要因超时更换键。202（已接受）只表示消息与运行请求已持久化，后续依然可能因权限、积分、预算或执行失败而终止。网络响应丢失不代表提交一定未成功。

## 2. 数据库容量保护

Chat 与 Run Control 新增可配置连接池和等待总量门禁。默认连接池 10、最多额外等待 64，即每进程最多 74 个顶层数据库操作。一次事务内多条查询只占一个操作槽。达到上限立即返回 503，不再向连接池追加无限等待；连接获取超时仍为 3 秒，语句超时仍为 8 秒。

这些限制是单进程的，不是数据库服务器的总连接数。生产需要计算所有服务、所有副本、迁移、运维和监控连接的总和。不要把每个副本的连接池同时调得很大。

后台投递在事务中等待有界网络确认，因此会占连接。Chat 后台最多约为发布工作数加 1；Run Control 约为投递工作数乘 2，再加发布、清理及消息接收。应给前台查询、续租和授权检查预留足够连接。当前没有独立的后台/前台连接池或硬连接预留，盲目增大后台并发可能反而拖慢续租。

新增内部指标 `db_operations`（当前数据库操作数）、`db_capacity`（容量）、`db_rejected_total`（拒绝累计数），分别带 `dsh_chat_` 和 `dsh_run_control_` 服务前缀。前两项为 Gauge（瞬时指标），最后一项为 Counter（累计计数），进程重启会重置。它们是本副本数据；原有队列积压指标仍是整个数据库的数据，不能将其按副本简单相加。数据库过载时抓取可能返回 503，应同时监测抓取失败。

## 3. 持久消息与结果投递

此前 Chat 每处理一批，即使仍有积压也等待 500 毫秒；Run Control 将清理、结果回写和事件发布串在同一循环，每轮同样等待。

现在有工作就继续处理，并主动让出事件循环；空闲或出错才退避并加入随机抖动。Chat 默认两个发布工作循环，仍以会话行锁确保同一会话顺序，不同会话可以并行。审计使用独立循环。

Run Control 将超时清理、回答回写、公开事件和支撑票据投递分开。回答回写与支撑票据默认各两个工作循环。使用 `SKIP LOCKED`（跳过已锁行）分配票据；确认丢失仍可能重投，由接收方幂等处理。不同运行的独立票据允许乱序，积分服务已有调用去重和终态调用数屏障，不能在这里移除它们。

所有工作数均有上限；停机停止领取新任务并等待已在途工作。网络失败保留持久票据，不以内存队列替代数据库发件箱。

## 4. 排队调度与执行槽

调度默认全局最多 64、每公司最多 32、每用户最多 2 个活动运行。达到调度上限的任务保留排队，不先交给执行器再立即拒绝。取消但尚未确认停止且租约仍有效的运行继续占槽位。

低负载公司/用户优先；等待超过默认 60 秒后，同等可调度条件下老任务优先，仍不能越过公司、用户和同会话顺序限制。统计活动负载时一次聚合，不再为每个候选任务反复扫描统计。同会话前一结果尚未完成回写时，仍不领取下一任务。

调度上限是独立的资源策略，建议不高于 Quota 的对应并发上限，但不跨服务读取配额数据库。**这不是完整的配额感知排队**：保守预算、积分、迟到的配额关闭以及不同运行状态仍由 Quota 最终判断，输入阶段可能被拒绝。没有自动把这种失败重放为新模型执行。

Runtime 每副本默认一个槽，可配置 1–16 个。各槽使用独立 DSH 子进程，继续遵守租约、工作流、工具和积分规则。默认并发不自动调高，也不自动启用模型。每个子进程有独立堆限制，但实际内存还包括原生内存、父进程、缓冲区；配置 16 不意味着 1 GiB（吉比字节）容器可以安全运行 16 槽。

例如 8 个执行副本 × 每副本 4 槽，理论最多 32 个执行任务，还要受到全局/公司/用户调度上限、配额以及供应商吞吐约束。如果每次对话平均占槽 30 秒，32 槽的理想吞吐约为每秒 1.07 次完成；一万个请求必须排队。这是算术示例，不是实测性能。

## 配置表

| 配置 | 默认 | 所属服务/意义 |
| --- | --- | --- |
| `API_MAX_IN_FLIGHT` | 128 | API 单副本在途请求上限 |
| `CHAT_MESSAGES_PER_MINUTE` | 120 | Chat 每用户每 60 秒新消息数 |
| `CHAT_PENDING_PER_USER` | 1000 | Chat 每用户未投递运行请求数 |
| `CHAT_PENDING_PER_SESSION` | 100 | Chat 每会话未投递运行请求数 |
| `CHAT_PUBLISH_WORKERS` | 2 | Chat 发布工作循环数，1–8 |
| `DB_POOL_MAX` | 10 | Chat/Run Control 各自数据库连接池，1–100 |
| `DB_MAX_WAITING` | 64 | 各自额外等待数据库操作数，0–1000 |
| `RUN_DELIVERY_WORKERS` | 2 | Run Control 支撑/回写各自工作数，1–8 |
| `RUN_MAX_ACTIVE` | 64 | Run Control 全局活动运行数，1–1000 |
| `RUN_USER_ACTIVE` / `RUN_TENANT_ACTIVE` | 2 / 32 | 用户 / 公司调度上限 |
| `RUN_AGING_SECONDS` | 60 | 排队老化优先阈值秒数 |
| `RUNTIME_CONCURRENCY` | 1 | Runtime 单副本执行槽数，1–16 |

Compose（容器组合编排）文件用 `CHAT_DB_POOL_MAX`、`CHAT_DB_MAX_WAITING`、`RUN_DB_POOL_MAX`、`RUN_DB_MAX_WAITING` 分别映射各服务通用数据库变量。Kubernetes（容器集群编排）中在对应工作负载设置。计数和调度限制需要所有同类副本使用一致值，否则混合版本的较宽策略可能多放行。

## 验证方式与升级

本轮 Chat 需第五版迁移，Run Control 需第六版迁移。维护窗口暂停新写入、停止旧执行器/运行控制、处理在途任务并备份数据库，再执行对应迁移，更新全部镜像与配置；不要让没有限流逻辑的旧 Chat 副本继续接收写入。迁移不删除旧消息和账本。

本机合成消息测试：

```powershell
$env:LOAD_USERS = "1000"
$env:LOAD_CONCURRENCY = "32"
npm run test:load:chat
```

过载测试可设 `LOAD_USERS=10000`（一万个用户）、`LOAD_CONCURRENCY=128`（128 个客户端在途请求）、`LOAD_API_CAPACITY=32`（32 个入口槽位）。还可设置 `LOAD_DB_CAPACITY`（数据库操作总容量，默认 74）。脚本只启动回环地址服务和临时 PGlite（轻量 PostgreSQL 引擎），不会读取真实账号或调用外部模型，结束关闭临时实例。

结果包含状态码分布、请求吞吐、成功接收吞吐、延迟分位数、持久消息/任务请求数和幂等重放一致性。错误返回很快，因此**不能用包含拒绝数的吞吐冒充有效处理能力**。此脚本不运行消息代理、调度器、模型和 SSE（服务器发送事件）链路，也不验证真实身份系统和原生数据库并发。

实测与失败记录见 [本机负载记录](load-test-results.zh-CN.md)。下一阶段仍需：原生 PostgreSQL 多连接锁竞争验证；完整链路压测；全局队列容量与拒绝/恢复协议；所有接口分布式限流；按会话分片的任务消费；调度器去全局热点；供应商请求/词元速率控制；真正的配额感知排队与集群扩缩容验收。

当前 NATS 运行请求消费者仍只允许一个未确认消息，调度仍持有全局短事务锁，Quota 预留仍按公司串行。它们是进一步提升吞吐的明确瓶颈，不因增加 API/Runtime 副本自动消失。本轮保留这些一致性边界，尚未宣称达到一万 QPS 或一万同时模型对话。
