# 按模型用量计价的积分账户

本轮实现第一种方式：供应商实际报告的 Token（词元）数量 × 平台管理员配置的模型单价，计算人民币金额，再按配置的兑换比例扣积分。不是固定每条消息扣分，也不是按最大输出预算扣费。

这里的金额是按配置算出的费用，不代表已与供应商正式账单核对；优惠、税费和供应商账单舍入可能不同。示例价格仅用于演示，不是 DeepSeek（深度求索）的实际报价。

## 服务职责与隔离

| 项目 | 职责 |
| --- | --- |
| `dsh-agent-quota`（配额与积分服务） | 持有价格版本、公司未分配积分、员工独立账户、冻结、结算、流水及受控管理命令 |
| `dsh-agent-run-control`（运行控制服务） | 从冻结定义取得模型标识，运行前请求预留；核验用量身份，持久重传；终态发送已开始的调用总数 |
| `dsh-agent-runtime-dsh`（DSH 执行服务） | 延用供应商计量上报，不接触积分账户，不提交价格、金额或积分数 |
| `dsh-agent-api`（前端聚合服务） | 身份校验后代理本人余额与流水；不计算价格，不开放充值、分配或扣费写接口 |
| `dsh-agent-contracts`（协议包） | 定义严格的数据格式与自动生成的 OpenAPI（开放接口描述规范） |

不新增服务或跨服务数据库查询。Quota（配额服务）自身 PostgreSQL（关系型数据库）事务完成用量入库、账户扣减及账本写入；一项失败全部回滚。

公司与员工分账。例如公司发放 100 积分，分配给五人各 20：公司未分配余额变为零，每名员工可用 20；员工不能自动借用公司剩余积分、其他员工积分或本人其他运行已冻结的积分。身份按租户与用户联合隔离，同名用户在不同公司也不是同一账户。

## 计价与精度

币种当前仅支持 CNY（人民币），没有外币汇率转换。金额、积分以及配置采用十进制字符串；最多六位小数。内部以 BigInt（大整数）和数据库精确数值计算，不使用浮点数计费。

每次模型调用分别计算：

1. 人民币费用 =（普通输入词元 × 普通输入单价 + 缓存命中词元 × 缓存单价 + 输出词元 × 输出单价）÷ 1,000,000，向上取整到 0.000001 元。
2. 扣减积分 = 人民币费用 × 每元积分数，再向上取整到 0.000001 积分。
3. 多次调用的积分相加；不在整次运行结束时重新合并取整。推理词元已包含在输出里，不能重复计费。

例如普通输入 1 元/百万词元、缓存 0.5 元/百万词元、输出 2 元/百万词元，1 元兑换 100 积分：输入 1000、缓存 200、输出 500，对应 0.002100 元、0.210000 积分。价格及比例均由管理员配置。

未报告缓存细分且缓存/普通输入价格不同，则无法准确计算，保留待结算；两者价格相同才可按总输入计价。用量缺失不视为零；已上报完整的零用量可以结清零费用。

## 价格版本与运行冻结

`POINTS_BILLING_ENABLED`（积分计费启用开关）默认 `false`（关闭）。开启时，运行控制下发执行输入前，由配额服务在同一事务中执行原配额检查和积分检查：

- 模型未配置有效价格：拒绝下发输入，返回 `DEPENDENCY_UNAVAILABLE`（依赖不可用）。
- 员工可用积分不足或已有待结算运行：返回 `QUOTA_EXCEEDED`（超出配额）。
- 检查通过：冻结指定的单次积分预算，并保存模型价格、兑换比例的快照。

同一价格版本不可覆盖；修改任何配置须使用新的 UUID（通用唯一标识符），发布后成为该模型的当前版本。重新发布已有相同版本会重新激活它，不修改历史。运行沿用预留时的快照，不因随后涨价、降价或调整兑换比例而重算。关闭开关只影响后续新增预留，已经建立快照的运行仍结算；旧的无积分快照运行不追溯收费。

`reservePointsPerRun`（单次运行冻结积分）是管理员设置的预留值，**不是供应商真实费用的硬上限**。它必须覆盖合理的输入、输出、多轮及工作流开销。实际费用超过剩余冻结额时，可以使用本人尚未冻结的可用余额；仍不足则保留 `pending_balance`（余额不足待结算），不透支。已发出的模型请求可能继续产生费用，不能将此机制宣传为绝对零欠费保障。

严格供应商费用上限、逐调用动态追加预留与中断机制尚未实现。默认不开启积分计费，必须评估预留额度与风险后启用。

## 可靠结算与异常处理

每次调用按运行、尝试、调用序号唯一计费。重复投递或确认丢失不会重复扣费；相同终报的不同用量拒绝覆盖。调用最终报告可以先于开始事件到达。

运行控制结束时通过 Outbox（事务发件箱）发送 `expectedCalls`（已开始调用总数）。即便关闭先到，只有配额服务收到对应数量的全部调用、且每项都成功结算，才释放剩余冻结积分。取消、超时和失败并不等于免费：已发生的调用仍结算，迟到报告沿用旧快照。零调用终态可以释放全部冻结额。原来的每日保守输出词元预算不退还，和积分账户相互独立。

`pending_usage`（用量缺失待结算）或余额不足时保存状态并确认接收，避免持续重传同一有效报告。关闭后尚缺调用或终报也计为待结算运行，暂停该用户新预留。积分冻结不会因并发预留过期而自动解除。

余额不足可以由运维补充分配后执行 `reconcile`（重新结算）命令；重复执行安全。它只能重新计算已有可信数据，不能补造词元。已保存的未知终报不可被这个命令更改，目前没有人工改单、缺失计量补录或退款协议。缺失报告可能长期冻结余额，需要运维调查，不能直接删除账本或把未知改成零。

## 受控配置与管理

先构建项目并执行配额第三版迁移。可信平台运维在设置了 `DATABASE_URL`（配额数据库连接串）的受控环境中，从仓库根目录运行：

```powershell
node dsh-agent-quota/dist/points-admin.js --file dsh-agent-quota/examples/pricing.example.json
```

实际执行前复制并修改示例，不要原样用于生产；其中 `configure-model` 是模型占位名。命令不会调用模型。配置字段如下：

| 字段或命令 | 中文含义 |
| --- | --- |
| `kind: price` | 发布并激活模型计价版本 |
| `policy` / `id` | 计价策略 / 唯一版本标识 |
| `provider: deepseek-official` / `model` | 深度求索官方供应商 / 与定义一致的模型名 |
| `currency: CNY` | 人民币，当前唯一支持币种 |
| `inputPerMillion` / `cacheReadPerMillion` / `outputPerMillion` | 每百万普通输入 / 缓存命中 / 输出词元的人民币单价 |
| `pointsPerYuan` / `reservePointsPerRun` | 每元积分数 / 单次运行冻结积分，均须大于零 |
| `kind: grant` / `kind: allocate` / `kind: reconcile` | 发放公司积分 / 分配员工积分 / 重新结算 |
| `tenantId` / `uid` / `runId` | 公司标识 / 员工标识 / 运行标识 |
| `points` / `operator` / `reason` | 积分数量 / 运维操作人标识 / 操作原因 |

公司发放命令文件示例：

```json
{"kind":"grant","id":"01990000-0000-7000-8000-000000000012","tenantId":"company-a","points":"100","operator":"platform-admin","reason":"演示公司积分发放"}
```

员工分配命令文件示例：

```json
{"kind":"allocate","id":"01990000-0000-7000-8000-000000000013","tenantId":"company-a","uid":"employee-1","points":"20","operator":"platform-admin","reason":"演示员工额度分配"}
```

将文件路径传给相同的 `--file`（命令文件）参数。五名员工分别使用不同操作标识；重试同一操作必须保留原标识和完整正文。相同标识但正文不同会冲突，不能当作新充值。发放、分配和扣费记录都有追加写保护，但数据库所有者仍有高权限，不等于防篡改审计系统。

重新结算命令格式为 `{"kind":"reconcile","runId":"实际运行的 UUID"}`。成功响应 `recorded: true`（已处理）不保证欠缺计量已经解决，需核对余额、待结算数以及运维数据库记录。

这不是支付充值服务，也没有面向公司管理员的自助接口。运维提供的操作人标识仅是审计字段，不是认证凭证。执行人必须核验公司、员工成员关系及发放依据；不能把命令文件生成和执行权限交给终端用户。现有 IAM（身份与访问管理）尚未提供完整公司成员与管理员授权管理。

## 本人查询接口

`GET /api/v1/points`（读取本人积分）返回 `balance`（余额）、`held`（冻结）、`available`（可用）、`billingEnabled`（新运行计费是否启用）和 `pendingRuns`（待结算运行数）。可用 = 余额 − 冻结。

`GET /api/v1/points/ledger`（读取本人流水）支持 `limit`（每页数量，1–100）和 `after`（上一页游标），响应 `items`（记录列表）及 `nextCursor`（下一页游标）。记录包含类型、`delta`（积分变动）、`createdAt`（入账时间），扣费项还包含运行、`attempt`（尝试编号）、`call`（调用序号）、`amountCny`（人民币金额）、`pricingId`（计价版本）。这里只列已入账流水，不列尚未结算的费用。

两者只查询经认证的当前用户，不接受用户或公司覆盖参数。金额和积分响应固定六位小数。本人接口不展示公司总余额、其他员工余额或运维操作原因。用量异步汇总，因此刚结束时余额和运行状态可能暂时不同步。

## 升级、验收与剩余边界

维护窗口暂停新请求并停止旧执行器/运行控制，处理在途任务、备份数据库。执行配额第三版迁移，升级配额、聚合接口和运行控制；全体旧运行控制退场后，再配置价格、发放/分配积分，最后统一开启积分计费。混用旧运行控制会缺少调用总数，无法安全释放冻结。所有配额副本必须使用一致的开关值，不能分批混用开启与关闭的副本。

Docker Compose（容器组合编排）与 Kubernetes（容器集群编排）模板均默认关闭积分开关。没有新增密钥、端口或服务。执行器启用仍是独立决定，启用积分不会自动调用模型。
